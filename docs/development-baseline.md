# Yellow War（黄色伙伴战争）第一版完整开发文档

**版本：** V1.0\
**文档状态：** 第一版开发基线\
**目标：**
做出一款能在浏览器直接打开、能完整玩完一局的横版即时战略小游戏，并通过
GitHub Pages 免费发布。

------------------------------------------------------------------------

## 1. 项目定位

### 1.1 项目目标

开发一款受经典横版即时战略玩法启发的原创小游戏。玩家经营经济、招募单位、指挥军队推进，摧毁敌方基地获胜。

第一版必须是**真正可玩的完整闭环**，不是静态角色展示页，也不是只有按钮的
UI Demo。

### 1.2 美术硬性要求

用户提供的六角色阵容图是第一版唯一角色美术基准：

1.  矿工（Miner）
2.  剑士（Swordsman）
3.  弓箭手（Archer）
4.  盾矛兵（Spearman）
5.  法师（Mage）
6.  巨人（Giant）

第一版直接使用对应的独立 PNG
立绘。不得用火柴人、圆点、emoji、彩色圆球或临时简笔画替代角色；不得擅自重新设计角色的颜色、脸、身体比例、装备和整体风格。

角色素材目前是**正面静态立绘**，不是行走/攻击序列帧。第一版用完整立绘作为游戏
Sprite，通过水平移动、左右翻转、轻微位移/缩放、武器特效、受击闪白和死亡淡出等方式表现动作。不得声称已经有真实骨骼动画。

### 1.3 第一版交付边界

**必须完成：**

-   开始菜单、战斗场景、暂停、胜负结算、重新开始
-   双方基地和基地生命值
-   矿工自动采矿、回基地交金币
-   六种兵种全部可招募
-   近战、远程、范围伤害和基础受击反馈
-   玩家进攻/防守/集合指令
-   敌方 AI 自动采矿、生产和进攻
-   摧毁敌方基地获胜，己方基地被摧毁失败
-   音量设置和本地设置保存
-   GitHub Pages 部署，公开链接可访问

**第一版不做：**

-   在线联机、账号、排行榜服务器
-   真实支付、后端 API、数据库
-   多章节战役、地图编辑器
-   装备掉落、复杂技能树、英雄养成
-   复杂寻路、复杂物理破坏
-   六种兵种的完整逐帧动画

## 2. 技术选型

### 2.1 最终技术栈

  层次       技术                            用途
  ---------- ------------------------------- ---------------------------------------
  游戏引擎   Phaser 4.2.1                    2D 渲染、场景、输入、相机、精灵和特效
  开发语言   TypeScript                      单位、状态机、经济和战斗逻辑
  构建工具   Vite                            本地开发、打包静态资源
  UI         Phaser Game Objects             游戏内 HUD、按钮、面板
  存储       localStorage                    音量、设置、教程状态
  版本管理   Git + GitHub                    源码管理
  发布       GitHub Pages + GitHub Actions   自动构建并发布静态网站

**版本说明：** 本项目从新项目开始，采用 Phaser 4，不从 Phaser 3
起步。不要混用 Phaser 3 教程里的旧渲染管线、插件和 API 写法。具体 API
以锁定安装版本的 Phaser 4 官方文档为准。

### 2.2 为什么不需要后端

第一版只有单人对战：

-   玩家操作在浏览器本地执行
-   敌方 AI 在浏览器本地运行
-   金币、生命值、单位状态在内存中维护
-   设置写入 localStorage
-   所有图片、音效和脚本由静态文件加载

所以不需要 Java、Spring Boot、MySQL、Redis 或云服务器。GitHub Pages
只负责托管 HTML、JS、CSS 和图片，不负责运行游戏逻辑。

### 2.3 初始化命令

建议使用 Node.js LTS 和 npm：

``` bash
npm create vite@latest yellow-war -- --template vanilla-ts
cd yellow-war
npm install
npm install phaser
npm run dev
```

第一次安装后提交 `package-lock.json`，后续用 `npm ci`
保证依赖可复现。Phaser 版本通过 lockfile 固定，不在每次构建时漂移。

## 3. 游戏体验与画面规格

### 3.1 画面规格

-   设计分辨率：1280 × 720
-   画面比例：16:9
-   方向：横屏
-   桌面端：优先完整展示战场和招募面板
-   手机端：横屏游玩，按钮可触摸，避免小于可操作尺寸
-   Phaser Scale：使用 FIT 思路保持比例，空余区域用背景填充
-   游戏暂停时冻结战斗时间，UI 仍可操作

### 3.2 场景布局

从左到右：

1.  玩家基地（左侧）
2.  玩家矿区（左侧偏中）
3.  中央交战区域
4.  敌方矿区（右侧偏中）
5.  敌方基地（右侧）

建议地面基线约为屏幕高度的 82%。角色以脚底为锚点（origin
bottom-center），这样角色移动时脚不会漂浮。

### 3.3 美术规则

-   角色必须使用本项目素材包内的六个 PNG。
-   角色显示高度建议：普通单位约 145--175 px；巨人约 205--245 px。
-   不得把角色缩成无法辨认的小图标。
-   玩家单位朝右，敌方单位通过水平翻转朝左。
-   阵营差异优先用脚下阵营光圈、血条颜色、基地旗帜和 UI
    表示，不改变角色主体颜色。
-   角色层级应高于地面、低于 HUD；同一战线按脚底 y 坐标排序。
-   角色被点击/选中时，可显示细描边或脚下圆环，但不能遮住角色主体。
-   第一版不使用素材图上的白色背景；PNG 应保留透明通道。

### 3.4 第一版角色素材

将素材 ZIP 解压，把六个角色放入：

``` text
public/assets/characters/
  miner.png
  swordsman.png
  archer.png
  spearman.png
  mage.png
  giant.png
```

另保留原始阵容图作为美术验收基准，不直接作为游戏单位 Sprite。

## 4. 核心玩法规则

### 4.1 开局状态

每局开始时：

-   玩家基地生命值：1800
-   敌方基地生命值：1800
-   玩家初始金币：400
-   敌方初始金币：400
-   双方各自拥有 1 名初始矿工
-   人口上限：30（每个单位占 1 人口）
-   双方矿工自动开始采矿
-   战斗单位初始为空，玩家可以立即招募

以上数值是第一版初始平衡值，后续通过配置文件调节，不散落在代码里。

### 4.2 经济系统

每一方有自己的矿点，避免第一版因争抢同一矿点产生复杂寻路。

矿工循环：

`前往矿点 → 采矿 → 返回基地 → 存入金币 → 再次前往矿点`

初始建议：

-   采矿耗时：2.5 秒
-   每次交付：55 金币
-   矿工被攻击时可死亡
-   矿工遇到敌军接近时优先撤回己方基地
-   矿工不主动追击敌方单位
-   矿工死亡后不会自动复活，需要重新招募

金币只允许通过经济系统增加，通过招募系统扣除。所有金币变化必须有明确来源，不能由
UI 自行修改。

### 4.3 六种兵种初始数值

  兵种       招募成本   生命值   攻击伤害   攻击间隔   攻击距离   移动速度
  -------- ---------- -------- ---------- ---------- ---------- ----------
  矿工            100      100          5     2.0 秒         35         75
  剑士            150      180         26     1.1 秒         55         85
  弓箭手          220      105         18     1.8 秒        250         58
  盾矛兵          250      280         34     1.5 秒         70         55
  法师            320      130         42     2.7 秒        220         48
  巨人            500      900         90     2.4 秒         85         32

说明：

-   攻击距离和移动速度均为游戏世界单位，不是现实单位。
-   盾矛兵受到的伤害降低 20%，第一版不区分攻击来源。
-   法师攻击命中后，对目标周围 55 px 范围造成 50% 溅射伤害。
-   巨人攻击命中后，对目标附近 45 px 范围造成 35% 溅射伤害。
-   弓箭手和法师使用投射物；剑士、盾矛兵、巨人使用近战攻击。
-   矿工攻击仅用于被迫自卫，伤害很低。
-   数值只是第一轮可玩平衡，不承诺最终平衡；必须经过实测调整。

### 4.4 招募规则

招募流程：

1.  玩家点击兵种按钮。
2.  检查当前金币是否足够。
3.  检查人口是否达到上限。
4.  检查基地是否仍然存活。
5.  扣除金币。
6.  在己方基地生成单位。
7.  单位进入默认指令状态。

如果金币不足、人口已满或基地已被摧毁，招募失败并给出明确 UI
提示，不扣金币。

### 4.5 战斗规则

-   战斗单位默认向敌方推进。
-   发现敌人后，优先选择攻击范围内最近的敌人。
-   目标不在攻击范围内：移动靠近。
-   目标进入攻击范围：停止移动并按攻击间隔攻击。
-   目标死亡：重新寻找下一个目标。
-   当前区域没有敌军：向敌方基地推进。
-   到达基地攻击距离：攻击敌方基地。
-   单位生命值小于等于
    0：进入死亡状态，停止寻敌、攻击和碰撞，播放短暂淡出后销毁对象。

第一版不做复杂 A\*
寻路。双方单位在一条主战线上移动，通过最小间距、轻量位置分离和 y
轴层级避免完全重叠。

### 4.6 玩家指令

第一版提供三个全军指令：

  指令   行为
  ------ ------------------------------------------------------
  进攻   向敌方推进，遇敌优先交战
  防守   不主动越过己方防线，攻击进入警戒范围的敌人
  集合   回到己方集合点附近，重新编队；遇到近距离威胁仍可自卫

指令只作用于战斗单位，不改变矿工的采矿循环。后续可扩展单体选择，但第一版不做复杂编队拖拽。

### 4.7 敌方 AI

敌方使用与玩家相同的单位规则和资源限制，不能作弊生成无限金币。

AI 每 4 秒评估一次：

1.  检查当前金币和人口。
2.  检查现有单位构成。
3.  若矿工不足，优先补矿工。
4.  若前排不足，优先剑士或盾矛兵。
5.  若远程单位不足，补弓箭手或法师。
6.  金币充足且人口允许时，有一定概率训练巨人。
7.  根据己方战线压力决定进攻或防守。

AI 使用权重和冷却时间，避免每帧随机招兵。AI
的金币来源必须来自其矿工交付。

## 5. 状态机设计

### 5.1 战斗单位状态

``` text
SPAWNING
   ↓
IDLE / ADVANCING
   ↓
SEEKING_TARGET
   ↓
ATTACKING
   ↓
TARGET_DEAD → SEEKING_TARGET
   ↓
DYING
   ↓
DESTROYED
```

状态切换必须集中在 Unit 状态机中，不允许多个系统同时随意修改单位状态。

### 5.2 矿工状态

``` text
GO_TO_MINE
   ↓
MINING
   ↓
RETURN_TO_BASE
   ↓
DEPOSIT_GOLD
   ↓
GO_TO_MINE
```

若检测到威胁：

`任意采矿状态 → RETREAT_TO_BASE`

威胁解除后，重新开始采矿循环。

### 5.3 对局状态

``` text
MENU
  ↓
PREPARING
  ↓
PLAYING
  ├── PAUSED
  ├── VICTORY
  └── DEFEAT
```

只有 `PLAYING` 状态推进战斗计时。`PAUSED` 时所有单位、投射物、经济计时和
AI 计时都必须停止。

## 6. 核心数据结构

### 6.1 兵种配置

兵种数据集中定义，不在不同模块重复写数值：

``` ts
export type UnitType =
  | 'miner'
  | 'swordsman'
  | 'archer'
  | 'spearman'
  | 'mage'
  | 'giant';

export interface UnitConfig {
  type: UnitType;
  cost: number;
  maxHp: number;
  damage: number;
  attackInterval: number;
  attackRange: number;
  moveSpeed: number;
  displayHeight: number;
  attackKind: 'melee' | 'projectile' | 'aoe';
}
```

### 6.2 单位运行时数据

``` ts
export type Team = 'player' | 'enemy';

export type UnitState =
  | 'spawning'
  | 'idle'
  | 'moving'
  | 'seeking'
  | 'attacking'
  | 'mining'
  | 'retreating'
  | 'dying';

export interface UnitRuntime {
  id: string;
  type: UnitType;
  team: Team;
  hp: number;
  maxHp: number;
  state: UnitState;
  targetId?: string;
  attackTimer: number;
  moveDirection: -1 | 1;
}
```

### 6.3 对局状态

``` ts
export interface MatchState {
  status: 'menu' | 'playing' | 'paused' | 'victory' | 'defeat';
  playerGold: number;
  enemyGold: number;
  playerPopulation: number;
  enemyPopulation: number;
  playerBaseHp: number;
  enemyBaseHp: number;
  command: 'advance' | 'hold' | 'rally';
}
```

实际实现时，Phaser Game Object 与纯业务状态分开。不要把所有数据都塞进
Sprite 对象。

## 8. 更新循环与性能约束

Phaser 场景每帧更新时：

1.  检查对局是否处于 PLAYING。
2.  更新经济计时。
3.  更新敌方 AI 决策计时。
4.  更新单位状态机。
5.  更新移动与位置分离。
6.  更新战斗、投射物和伤害。
7.  更新基地生命值。
8.  检查胜负。
9.  刷新必要的 UI 数据。

性能原则：

-   不要每帧创建临时对象或重复查询全场所有单位。
-   单位集合按阵营维护。
-   目标搜索优先检查附近单位；第一版单位数量较少，可先用简单距离遍历。
-   投射物结束后销毁或回收到对象池。
-   受击特效和血条不能无限创建。
-   暂停时停止游戏计时，不只是盖一层暂停图片。
-   第一版目标：桌面端约 60 FPS；普通手机横屏尽量稳定在 30 FPS 以上。

## 10. GitHub Pages 部署

### 10.1 Vite 配置

如果仓库名是 `yellow-war`，项目页地址会类似：

`https://你的GitHub用户名.github.io/yellow-war/`

`vite.config.ts` 中需要配置：

``` ts
import { defineConfig } from 'vite';

export default defineConfig({
  base: '/yellow-war/',
});
```

如果使用 `用户名.github.io` 根仓库或自定义域名，则 `base` 通常使用 `/`。

### 10.2 package.json 脚本

``` json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview"
  }
}
```

### 10.3 发布流程

1.  创建 GitHub 仓库。
2.  将源码推送到 `main`。
3.  在 GitHub 仓库 Settings → Pages 中选择 GitHub Actions。
4.  配置 workflow：安装依赖、执行 build、上传 `dist`、部署 Pages。
5.  查看 Actions 是否成功。
6.  打开 Pages 给出的 URL 测试。
7.  后续推送到 `main` 自动重新部署。

注意：不要把 `npm run dev` 当作线上服务。线上必须使用 `npm run build`
生成的静态 `dist`。

-   首页可以打开。
-   所有角色图片均加载成功。
-   控制台没有资源 404。
-   刷新后游戏仍能启动。
-   GitHub Pages 子路径下图片和音效路径正确。
-   桌面 Chrome 和手机浏览器横屏均可操作。

## 13. 风险和处理原则

### 风险一：静态立绘没有真正的动作帧

第一版接受这一限制。通过整体位移、攻击前摇、武器特效、受击闪白和死亡淡出实现基础反馈。后续再为相同角色制作侧面动作帧，不更换角色设计。

### 风险二：正面角色左右翻转会显得不够侧面

第一版优先保留角色辨识度。角色可以做轻微倾斜、移动和层级变化，但不伪造复杂的
3D 旋转。后续美术迭代必须以原始阵容为参考。

### 风险三：战场单位重叠

第一版采用单战线、最小间距、轻量分离和脚底排序。不引入复杂寻路引擎。

### 风险四：数值不平衡

所有兵种成本、血量、伤害、攻速和速度统一放在配置文件中。每轮试玩后调整配置，不修改散落在业务代码中的常量。

### 风险五：GitHub Pages 资源路径错误

使用 Vite 的 `base` 配置和相对资源引用；部署前执行 build 和 preview
检查。
